The local model: a bundled engine, started for you

How the app gets an OpenAI-compatible LLM endpoint running on a user's Mac without them installing, configuring, or ever seeing llama.cpp.

Answer in one line: the engine is a pinned, checksummed release asset bundled into the app, the model is fetched once into the app's cache, and llama.cpp runs as a supervised child process on loopback — so the app owns its whole lifecycle, and the webview only ever reads a status event.

1 · Who talks to whom

The core relationship: one Rust process makes decisions, one C++ process does inference, and the only thing between them is argv on the way in and HTTP on the way out.

2 · What happens between launch and a usable endpoint

One async job, six published phases. Every arrow below is a status event the webview actually receives.

3 · Who owns the child process

A llama-server holding 5 GB of weights is expensive to leak. Four ways it can go wrong, and the guard for each. This is where review found three real bugs.

4 · Module map

Six files, each with one job. The seam is what makes the other five testable.

local_llm/mod.rs

The pipeline

run() = serve() then supervise(), or one published failure. Owns LlmStatus, the run id, the busy flag, and the single owned engine handle.

local_llm/engine.rs

The seam

trait Engine (locate / prepare / start) and trait Running (endpoint / poll_exit / log_tail / terminate). LiveEngine binds them to reality; tests bind them to a script.

local_llm/server.rs

The process

Builds argv, resolves the bundled binary, spawns, probes /health, tails the log, reaps orphans. Output goes to a file — a full pipe would block the child.

local_llm/model.rs

The weights

hf-hub snapshot_download, recursive GGUF discovery, case-insensitive quant match, and a reporter that folds per-file and xet progress into one increasing count.

scripts/provision-llama.mjs

The bundle

Downloads a pinned asset, verifies sha256, copies llama-server plus every @rpath dylib, rebuilds symlinks, stages into DEST.new and renames atomically.

src/ModelProgress.tsx

The surface

Listens, then reads the snapshot so a late mount still sees progress. Renders a bar, an indeterminate sweep, a failure with Retry, or nothing at all when running.

6 · Decisions worth arguing about

Each of these was chosen against a plausible alternative. Annotate any you disagree with.

subprocess, not in-process bindings

llama-server over HTTP

llama.cpp decodes one batch per context. The server's slot scheduler is what turns "summarise four pages" into four concurrent sequences, and a crash in the C++ backend then costs a restart rather than the window.

no PATH fallback

The bundle or nothing

A stray system llama-server is usually older and rejects -kvu / --kv-unified-per-slot. Finding one would turn a broken bundle into a confusing startup failure. The error says "reinstall", never "install a tool".

pinned tag + sha256

b11856, 16 244 700 bytes

"Whatever is newest" cannot reach a build. The digest catches a truncated or tampered asset. Other platforms fail loudly with instructions instead of guessing an asset name.

-np 4 -kvu --kv-unified-per-slot 8192

Four slots, one KV pool

With an explicit slot count and no -kvu, llama.cpp gives each slot a private KV buffer, so a shared prompt is never reused across concurrent requests. Verified against the real binary: -np 4 alone reports kv_unified = false.

--chat-template-kwargs

Thinking mode off

{"enable_thinking": false}. A page summary should not pay for a chain of thought before every answer.

Qwen3-8B · Q4_K_M

Apache-2.0, ungated

Chosen over Gemma 3n E4B: no gating, mature GGUF support, no PLE/AltUp complexity — the safer thing to ship inside an app.

7 · Deliberately not here yet

next

Nothing calls the endpoint

The search bar and the engine are not connected. BuddyAgent::with_endpoint(api_key, base_url, model, preamble) in src/agent/mod.rs already speaks OpenAI-compatible HTTP, so it is a wiring job, not a new abstraction.

open question

Where does the bearer token go?

The key is local-<pid> and is deliberately absent from LlmStatus — a status event is not a place for a secret. When the agent is wired up, how does it get the key without going through the webview?

pre-existing

Signing, and other platforms

The built app is adhoc-signed with no team id, and fails codesign --verify identically with the engine removed. Windows and Linux have no pin entry, so provisioning refuses rather than guesses.
